# API Design Conventions & Protocols

## 1. Overview & Architectural Standards

All HTTP APIs exposed by the **Edge API Gateway** (`apps/api-gateway`) and private domain microservices adhere to strict RESTful standards and unified JSON serialization rules.

### Core Principles
- **Transport**: HTTPS mandatory in production; HTTP allowed on internal Docker/Kubernetes container networks.
- **Base URI Pattern**: `/api/v1/{domain-prefix}/{resource}`
- **Data Format**: `application/json; charset=utf-8` for all requests and responses.
- **Traceability**: Every request carries an `x-correlation-id` and returns a `requestId` in the response metadata.
- **Statelessness**: No session cookies; all state authentication is Bearer JWT (client-to-gateway) and Signed Internal JWT (gateway-to-service).

## 2. Standard Response Envelope (Blueprint v2.0 Section 40)

Every API endpoint returns a standardized response envelope. Frontend clients must never parse raw arrays or unnested primitives.

### 2.1 Success Response Schema
```json
{
  "success": true,
  "data": {
    "orderId": "so_2026_001928",
    "orderNumber": "SO-2026-000042",
    "status": "CONFIRMED",
    "totalAmount": "18500.00",
    "currency": "EGP"
  },
  "meta": {
    "requestId": "req_88f912da-4a57-41eb-bc87-9bb3a6771d99",
    "timestamp": "2026-09-27T14:30:00.000Z"
  }
}
```

### 2.3 Reporting / CQRS Consistency Schema (Rule 17 & Blueprint v2.0 Section 38)
Analytical endpoints served from read projections return explicit eventual consistency metadata:
```json
{
  "success": true,
  "data": {
    "totalRevenue": "1250000.00",
    "grossProfit": "320000.00"
  },
  "meta": {
    "requestId": "req_99887766-5544-3322-1100-aabbccddeeff",
    "dataAsOf": "2026-09-27T14:28:45.120Z",
    "projectionLagMs": 350,
    "isEventuallyConsistent": true
  }
}
```

## 3. Standard Request Headers

| Header Name | Type | Presence | Description |
|:---|:---:|:---:|:---|
| `Authorization` | String | Required* | `Bearer <JWT_TOKEN>` (*except public endpoints like `/api/v1/auth/login`). |
| `Content-Type` | String | Required | Must be `application/json` for POST, PUT, PATCH. |
| `Idempotency-Key` | String | Required* | UUIDv4 identifying client execution (*mandatory on state-changing financial/stock writes). |
| `x-correlation-id` | String | Optional | Unique trace identifier; generated by Gateway if missing. |
| `x-company-id` | String | System | Extracted from verified JWT and injected by Gateway into downstream headers. |
| `x-branch-id` | String | Optional | Target branch scope context for active operation. |

## 4. Query Parameter Standards

### 4.1 Pagination
- `page`: 1-based integer (Default: `1`).
- `limit`: Number of items per page (Default: `20`, Maximum: `100`).

### 4.2 Sorting
- `sort`: Field name to sort by. Prefix with `-` for descending order.
- Examples:
  - `GET /api/v1/sales/orders?sort=-createdAt` (Newest first)
  - `GET /api/v1/inventory/products?sort=sku` (Alphabetical by SKU)

### 4.3 Date Range Filtering
- Standard ISO-8601 strings:
  - `startDate`: `2026-01-01T00:00:00Z`
  - `endDate`: `2026-01-31T23:59:59Z`

### 4.4 Status Filtering
- Multi-status comma-separated filters:
  - `GET /api/v1/sales/orders?status=PENDING,CONFIRMED`

## 5. HTTP Methods & Resource Semantics

| HTTP Verb | Operation | Idempotent | Safe | Typical Status Codes |
|:---|:---|:---:|:---:|:---|
| `GET` | Read resource or collection | Yes | Yes | `200 OK`, `404 Not Found` |
| `POST` | Create resource or execute Saga command | No* | No | `201 Created`, `200 OK`, `400 Bad Request` |
| `PUT` | Complete replacement of resource | Yes | No | `200 OK`, `404 Not Found` |
| `PATCH` | Partial update / state transition | No | No | `200 OK`, `409 Conflict` |
| `DELETE` | Soft delete / archive resource | Yes | No | `200 OK`, `204 No Content`, `409 Conflict` |

*\* POST operations with `Idempotency-Key` header are made idempotent by the API Idempotency layer (Blueprint v2.0 Section 29).*
